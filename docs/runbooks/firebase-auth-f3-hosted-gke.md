# F3 hosted GKE delivery: F4 prerequisites and rollback

This is an **opt-in, repository-only** F3 contract. Do not apply the hosted overlay until F4 is independently approved. The canonical GCP overlay remains private and contains a temporary Cognito/JWKS fixture; never attach a public Ingress to it directly.

## Build and provenance

1. Confirm remote main, independent review, cost/IAM approvals, and a measured free capacity budget on the retained `e2-standard-2` node. Record `kubectl describe node`, allocatable CPU/memory, requested resources and pending Pod events for backend, OpenSearch and the proposed 50m/64Mi frontend. Do not increase the node count or type under F3.
2. Obtain an **owned** HTTPS hostname and reserve a global external static IP name. Record DNS control, Firebase authorized-domain/project setup, and the GKE Ingress, NEG, BackendConfig, ManagedCertificate, firewall and Artifact Registry capabilities. These are F4 gates with possible continuing LB/IP/certificate charges.
3. Build `frontend/Dockerfile.hosted` from the `frontend/` context with public `REACT_APP_FIREBASE_API_KEY`, `REACT_APP_FIREBASE_AUTH_DOMAIN`, `REACT_APP_FIREBASE_PROJECT_ID`, `REACT_APP_FIREBASE_APP_ID`, and `HOSTED_HOSTNAME` build arguments. The Dockerfile fixes `REACT_APP_AUTH_PROVIDER=firebase`, relative `REACT_APP_API_BASE_URL=`, and disables browser preview. These web identifiers are public, never Admin credentials. Record the exact source SHA, build-arg identity, build artifact checksum, immutable remote image digest and registry provenance. Publish only with separate F4 authority; no mutable `latest` reference.
4. Replace **all** `REPLACE_WITH_*` values in the opt-in hosted manifests with independently checked values: same owned hostname in Ingress and ManagedCertificate, same Firebase project in issuer and `FIREBASE_PROJECT_ID`, reserved static IP name, reviewed backend/frontend SHA-256 digests. Keep `FIREBASE_BILLABLE_UIDS` empty until separate cost authority. Check rendered output for placeholders and any `identity.example.test`, Cognito client, test/local profile or fixture JWKS before applying.

## Ordered rollout and verification (F4 only)

1. Publish/verify the immutable images, render the hosted overlay and read back exact image digests. Supply the existing backend runtime secret using its approved private path; no secret belongs in frontend build args or ConfigMaps.
2. Apply hosted BackendConfigs and Service NEG annotations, frontend Deployment/Service and Firebase runtime ConfigMap patch; verify both Services are `ClusterIP`, NEG annotations and readiness on frontend `/healthz:8080` and backend `/actuator/health/readiness:8080`. Check Pod readiness and BackendConfig/NEG read-back **before** public routing. Do not bypass a failed capacity preflight.
3. Reserve/verify owned DNS and static IP, then apply ManagedCertificate and Ingress. Leave HTTP enabled while Google-managed certificate provisions; `kubernetes.io/ingress.allow-http=false` is deliberately absent. Wait for cert `Active`, matching DNS/TLS hostname, healthy load-balancer backends and required controller events. Only then separately review enabling the optional FrontendConfig HTTPS redirect. A redirect before certificate readiness can strand traffic.
4. From the public hostname verify HTTPS certificate and host routing, SPA root/deep link, `/static/*` immutable cache, `/index.html` no-store, unknown asset 404, mismatched Host denial, `/actuator`, `/internal`, `/metrics` and dotfile 404. Verify `/api` reaches Spring Boot with original Authorization and a protected endpoint returns JSON 401 without a token, while a valid Firebase ID token maps to its project owner. Check that neither Nginx logs nor artifacts contain bearer headers. No API failure may return React HTML.

`/api` is routed directly by GCE Ingress to the existing backend ClusterIP Service. The frontend Nginx is static-only and returns 404 for `/api` if reached directly. Nginx allows GKE `/healthz` probes on any Host; every other unmatched Host path returns 404. Backend internal and actuator paths are never routed to the backend by the Ingress.

## Rollback and cost closure

If readiness or authentication fails, stop new traffic and restore the previously reviewed backend/frontend digest and private routing; verify original health before removing the hosted Ingress. To dismantle the hosted surface, disable/remove Ingress and ManagedCertificate/FrontendConfig, inspect controller-created load balancer, forwarding rules, backend services, NEGs and reserved IP, then remove frontend workload and hosted Service annotations as approved. Preserve the canonical private overlay. DNS, Firebase authorized domains and registry objects need separate owner review. **GKE node count zero does not stop load-balancer, static-IP, storage or other retained-resource charges.** Record actual resource deletion and billing state; do not infer zero cost from idle Pods.
